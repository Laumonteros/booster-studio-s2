## Rules summary

- Autonomous robot soccer, **3 robots per team**, more valid goals wins. The example advertises Booster T1 and K1 support; this local run uses the bundled **K1** six-robot scene `mjcf/football_match_pitch_6_K1.xml`. Both K1 and T1 six-robot scenes are bundled. This is not a physical-robot match.
- Field **14 × 9 m**; goal **2.6 m wide × 1.8 m high × 0.6 m deep**; center-circle radius **1.5 m**; ball radius **0.11 m**.
- A goal adds one point when the **whole ball** crosses the goal line between the posts, below the crossbar, within the goal depth. Whole-ball crossing also governs out of bounds. After a goal, the conceding side kicks off.
- Regulation is **10 minutes of simulation time**, without a half-time split. The clock continues through goals, out-of-bounds and restarts. Qualifying/group matches can draw. Knockout ties use repeated **5-minute golden-goal** extra-time periods until a team leads. This local run uses the runtime's default `allow_draw` regulation mode, not a knockout configuration.
- Main phases: `initial → ready → set → playing → finished`; `stop`/referee pauses occur during play. READY permits movement into kickoff formation, can end after 5 s of continuous stability, and is forced after at most 45 s. SET waits approximately 5 s with robots stationary. SET and STOP require zero movement, not continued chasing/kicking.
- Kickoff exclusive time is **10 s**; other set plays allow **45 s**, then the ball opens. Opponents must remain more than **1.45 m** away, with safety margin, until the legal release/touch. Opponent-kickoff positioning must be outside the 1.5 m center circle; READY positions must be in one's own half.
- A taking team's goal following a set play requires **two different robot touches**, or the decisive touch more than **0.5 m from the restart point**. Simply waiting until the ball opens does not waive this requirement.
- Leaving the field, illegal motion during pauses, prohibited touches, inactivity near the ball, etc. can cause automatic pickup/penalties. Penalized robots must not return themselves. The sample's AGENTS.md notes a 10 s inactivity threshold when within 3 m of the ball.
- Agents must use permitted observations and actions only: do not read private simulator state, forge referee commands, connect to internal match-control endpoints, scan ports, or change strategy mid-match. The HTTP start/status calls and physics capture in this workspace are **local operator/debugging tools outside the agents**; neither strategy was modified to use them.

## Team/agent API

The official example is Python 3.10 in the Docker runtime, uses `booster_agent_framework`/BoosterOS/ROS 2 Humble, and declares entry `src/main.py:SoccerSimAgent`. It depends on `py_trees==2.4.0`; the runtime provides the platform SDK. `agent.toml` declares minimum API level 10700 and platforms `sim_x86_64`, `sim_aarch64`, `real_jetson`.

One agent controls all three teammates. Its main hook `play(context, players, store)` is called at approximately **30 Hz** and should return quickly (no blocking I/O or sleeps). `init_store(store)` initializes persistent state. The baseline selects the nearest eligible robot as attacker, a goal-side robot as goalkeeper, and the remaining robot as support.

Inputs (`Context`, read-only snapshot):

- `ball`: x/y, or `None` if stale (~1.5 s).
- `teammates`, `opponents`: robot ID → state, including `pose=Pose2D(x,y,theta)` or `None`.
- `game`: state, stopped flag, set-play type, kicking team, secondary time, remaining seconds, teams/scores/player penalties; can be `None`.
- `field`: length/width, circle/goal/goal-area/penalty-area geometry.
- `team_id`, `now`, `dt`.

Coordinates are **team-relative**: +x toward the opposing goal, origin at field center; do not mirror them again. `store` is a `SimpleNamespace`, accessed by attributes rather than dictionary methods.

High-level `Player` commands include `attack(kick_target=None)`, `guard()`, `support()`, `take_kickoff(kick_target=None)`, `move_to_position(target)`, `walk_to(target, face=None, avoid_ball=False, avoid_robots=False)`, `kick(direction,power)`, `release_kick()`, and `stop()`. Issue one high-level action per eligible robot per frame. `kick` starts a continuing kick task, not an instantaneous impulse; stop/release cancels it. Position/game/ball may be missing, and fallen/penalized robots must be filtered. `src/main.py`, `src/player.py`, `src/param.py` are intended strategy-edit locations; `src/framework/` is the platform layer and was left unchanged.

The project pins Studio scene `football3v3`, mode `soccer-match`, in `.booster-studio/project.json`. No sample strategy or metadata was changed. The optional `booster-3v3-soccer` skill was not present in the checked bundled/default skill locations; upgrade the development environment for its full automated rules checklist. This run is baseline execution, not certification that all strategy edge cases comply.

### Working CPU match route

This is a local developer route through the **bundled official runtime**, not a documented public competition CLI. No simulator/referee/strategy source was patched. The prepared image is local only and was not published. The original Studio container name was `92w4l-k1`:

```bash
S=/home/ubuntu/booster-studio
N=$S/app/usr/share/booster-studio/resources/app/booster-native/statics
docker cp "$S/sim-3v3-simple-framework/build/booster_champion_3v3-1.1.0.agent" 92w4l-k1:/tmp/sample.agent

  -p 127.0.0.1:38383:38383 \
  -v "$S/match-results:/match/results" \
  -e MODEL_PATH=mjcf/football_match_pitch_6_K1.xml \
  -e MATCH_RESULT_DIR=/match/results \
```

## Errors, workarounds, and limitations

1. Studio camera startup: `native camera renderer backend panicked during startup: Unable to find a GPU!` followed by `Make sure you have installed required drivers!` (`studio.log`). Physics/poses continued. Worked around for this match by running without Studio rendering and using CPU EGL for one snapshot. A Mesa Vulkan driver .deb was downloaded/extracted under `mesa/` during investigation, **not installed and not credited with fixing Studio rendering**.
2. Unsigned build: `[ERROR] Missing sign config: [sign] is not set and sign config is not provided` (`build.log`). Local-only signing allowed the build; official submission trust was not checked.
3. First raw extracted-agent launch: `executable 'pyagent_x86_64' not found on the libexec directory ...`. Python zip extraction had lost its executable bit; `chmod +x` fixed it and both agents subsequently became Active.
4. First attempt setting `MATCH_MODE=viewer` failed because competition mode requires a complete orchestrator environment: `ValueError: MATCH_REPLAY_ENABLED is required in match mode` and `ValueError: MATCH_RUNTIME_DIR is required in match mode` (`match-container.log`). Rather than inventing missing tournament settings, the successful local run leaves `MATCH_MODE` unset and uses the normal manual-start referee defaults. It is still **headless** in the ordinary sense (no graphics viewer process). Failed container: `booster-local-match`; successful run: `booster-local-match-2`.
5. First capture requested 1280 px against a 640 px offscreen framebuffer: `ValueError: Image width 1280 > framebuffer width 640.` Fixed in the capture-only model by setting `model.vis.global_.offwidth/offheight`; the subsequent capture succeeded.
6. Initial Studio SSH reset recovered automatically: `Connection reset by peer (os error 104)` then `SSH connection successful after 2 attempt(s)`. Nonfatal ROS setup warning refers to an image-build checkout path `/home/v-linux/gitee_go_agent/.../local_setup.bash`; required installed ROS libraries still loaded and both agents activated. Docker image does not include `rg`; filtering was performed on the host instead. No host dependency workaround was needed.
7. `playwright` is not installed (`ModuleNotFoundError: No module named 'playwright'`); existing Chrome CDP (`cdp.mjs`) was used for Feishu DOM extraction instead. One exploratory non-linked Feishu URL redirected to login; the linked public course/rules/submission content above had already been read. No credentials requested or entered.
8. This is local execution of an unmodified sample, not a competitive strategy benchmark, formal rule-compliance certification, or confirmation the event accepts locally signed packages. Newer Studio behavior is untested. No Isaac/CUDA/NVIDIA software was installed.
